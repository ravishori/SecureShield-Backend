## 3. The SQL file (reviewed, not executed)
Parts, in order, with the transaction structure that PostgreSQL requires (`CREATE DATABASE` cannot run in a transaction block, so do **not** use `psql --single-transaction`):
| Part | What | Transaction |
|---|---|---|
| 0 | precheck: loopback-or-socket server only, connected to `postgres`, PostgreSQL 15+, superuser | one `DO` block |
| 1 | create the three roles if missing (loop, `CREATE ROLE` only when absent); existing roles are never altered, only checked for excess privilege (corrected in Stage 1.2A) | one explicit `BEGIN`/`COMMIT` |
| 2 | `CREATE DATABASE` for each database, generated by `\gexec` only if absent, then an ownership check that aborts on a mismatch | **autocommit, outside any transaction** |
| 3 | `REVOKE ALL ... FROM PUBLIC` on both databases, `GRANT CONNECT` per role, explicit cross-database revokes | one explicit transaction |
| 4 | `\connect` to each database: revoke `PUBLIC` on schema `public`; development: `USAGE` plus default privileges for the app role; test: nothing else | one explicit transaction per database |
| 5 | verification: `SELECT` only, each with its expected result in a comment | none |

Safety properties checked by tests: no `DROP`, `TRUNCATE`, `DELETE`/`UPDATE`/`INSERT` statement, `COPY`, `ALTER SYSTEM`, `CREATE EXTENSION`, password literal, `GRANT ALL`, grant option or privileged attribute; `CREATE DATABASE` and `\connect` never inside `BEGIN`..`COMMIT`; transactions balanced; idempotent (`WHERE NOT EXISTS`); `ON_ERROR_STOP`; Part 5 is SELECT-only; the file ends back on `postgres`.
**Honest limits of the review:** it was reviewed by reading and static tests, never by a server. Items most worth a human look before running: the `\gexec` blocks, `ALTER DEFAULT PRIVILEGES FOR ROLE`, and that the new databases inherit encoding/collation from `template1` (verification query 5.3 shows the encoding; expect UTF8). If a role or database with one of these names already exists, the script reuses it without altering it and stops if it holds excess privilege or the database has a different owner (Stage 1.2A).

## 8. Security limitations and unresolved items
- **The SQL has never run.** Syntax and behaviour on a real server are unproven until step 2 above. (Medium, expected.)
- **Superuser needed once.** Parts 3-4 require the administrative role; that role's credentials are yours and are not stored anywhere. (Low.)
- **Server exposure not changed.** The local server listens on `*` according to the earlier audit. Hardening to `localhost` and SCRAM in `pg_hba.conf` is documented but deliberately not done by the script. (Medium until done.)
- **Legacy local `SecureShieldDB`.** It likely still exists on this server (Neon migration source). It is untouched, refused for development use by the backend, and only readable by the migration scripts with explicit confirmation. (Low.)
- **Test role has DDL rights inside its own database** (it must, for migrations and `TRUNCATE`); it has no access to any other database. (Low.)
- **Role names are cluster-global.** If an unrelated role of one of these names already exists, the script would reuse it (and only remove privileges). Check the Part 5.1 output. (Low.)
- **Placeholder passwords** in `.env.example` fail authentication if copied unchanged, never fall back to anything. (Informational.)
- **Not covered:** a tunnel that forwards the test database name `secureshield_test` to something else is caught only by the `current_database()` check against the name in the URL. (Low.)
