## 2. Priority 1 (critical protections)
### 2.1 `warrior_applications`: represent `uq_warrior_app_user_pending`
**Evidence.** Database: `CREATE UNIQUE INDEX uq_warrior_app_user_pending ON warrior_applications (user_id) WHERE (status = 'pending'::warriorapplicationstatus)` (revision 14). The model's docstring promises "one open application per user ... partial unique index ... in the Alembic migration" but declares nothing. The router (`app/routers/cyber_warrior.py:76-86`) checks first and returns 409, so the database index is the only **race-safe** guard; the test `test_second_pending_application_conflicts` exercises the router check, not the index. `alembic check` today proposes `remove_index uq_warrior_app_user_pending`: applying an autogenerated migration would silently remove the rule.
**Proposed model definition** (`app/models/cyber_warrior.py`, class `WarriorApplication`; add `Index, text` to the imports):
```python
__table_args__ = (
    Index("uq_warrior_app_user_pending", "user_id", unique=True,
          postgresql_where=text("status = 'pending'")),
)
```
Same pattern as the existing partial indexes in `app/models/app_install_event.py`, which `alembic check` already accepts without complaint [V: they were not reported in Stage 1.4]. The predicate semantics are unchanged (the database stores `status = 'pending'::warriorapplicationstatus`; Alembic does not rewrite or compare predicates). The existing `index=True` on `user_id` and `status` stays (they match `ix_warrior_applications_user_id/status`).
**Database impact:** none. **Risk:** none at runtime; metadata only.

### 2.2 `sms_sender_registry`: the "upper" index
**Evidence.** `app/models/sms_sender_registry.py:38` declares `Index("ix_sms_sender_header_upper", "header")`, a plain index on the raw column, with the name promising `upper`. The model also has `index=True` on `header`, which yields `ix_sms_sender_registry_header` (present in the database), so the model currently declares **two identical plain indexes**. The only lookup in the application (`app/services/sms_header_validator.py:151-153`) is `select(SmsSenderRegistry).where(func.upper(SmsSenderRegistry.header) == header.upper()).limit(10)`. PostgreSQL cannot use a plain btree on `header` for `upper(header) = :x`, so every lookup is a sequential scan of up to 23,192 rows (the documented size of the registry). The seed script stores headers trimmed but not upper-cased, so normalising the data is not guaranteed.
**Exact expression needed:** `upper(header)` (equivalently SQLAlchemy `func.upper(SmsSenderRegistry.header)`). It must match the query's expression for the planner to use it.
**Proposed model definition:**
```python
from sqlalchemy import Index, Integer, String, Text, text
...
__table_args__ = (Index("ix_sms_sender_header_upper", text("upper(header)")),)
```
(`header` keeps `index=True`; the plain index is still useful for exact matches and already exists. A `text()` expression is used because the mapped column object is not usable inside the class body; this is the same technique as the `created_at DESC` indexes below.)
**Proposed migration** (new file, section 6): `op.create_index("ix_sms_sender_header_upper", "sms_sender_registry", [sa.text("upper(header)")])`, downgrade `op.drop_index(...)`. The table is empty in `secureshield_dev` (no seed has run), so creation is instantaneous; on a seeded table of about 23k rows it is sub-second. Run it **before** seeding.
**Verification item (the one unknown):** how Alembic 1.13 compares an expression index whose reflected text is `upper((header)::text)` against the model text `upper(header)`. If `alembic check` reports a spurious change, change the model text to the reflected form `upper((header)::text)` (the index in the database is unaffected). This can only be settled by running `alembic check` against a migrated database (a later, separately approved step). It does not change the plan or the migration.
**Do not** seed anything as part of this work.

## 3. Priority 2: alignment details
All of these are **model-only** unless stated. Models never issue DDL in this project (no `create_all`; tests migrate with Alembic), so none of them changes a single runtime query. The guarantee that matters is that **`alembic check` becomes clean** and the next autogenerate is empty.
### 3.1 `warrior_audit_logs` (`cyber_warrior.py`, class `WarriorAuditLog`)
Database: `ix_warrior_audit_actor (actor_user_id, created_at DESC)`, `ix_warrior_audit_subject (subject_user_id, created_at DESC)`; **no** index on `action`; no table comment. Model today: `index=True` on `actor_user_id`, `subject_user_id`, `action`, plus the comment.
Code use: nothing in `app/` queries this table (it is written to, by the warriors router); the composite indexes serve "all events for user X, newest first" (the model's own comment says so), and an index on `action` has no consumer. **Proposed:** remove `index=True` from the three columns and declare
```python
__table_args__ = (
    Index("ix_warrior_audit_actor", "actor_user_id", text("created_at DESC")),
    Index("ix_warrior_audit_subject", "subject_user_id", text("created_at DESC")),
    {"comment": "Append-only. Do not UPDATE or DELETE rows here."},
)
```
Comment: the model carries it, the database does not. Two choices: (a) remove it from the model (no migration, loses the in-database documentation) or (b) apply it with `op.create_table_comment(...)` in the same new migration (recommended: comment-only, reversible, no lock beyond a catalog update). Plan assumes (b).
### 3.2 ON DELETE CASCADE (`behavior_event.py`, `community_scam.py`, `emergency_contact.py`)
Database: `ON DELETE CASCADE` (revision 8). Model: `ForeignKey("users.id")`. Account erasure (`app/services/account_erasure.py:139-144`) deletes these rows explicitly, so **nothing depends on the cascade**; the cascade is only a safety net. **Proposed:** `ForeignKey("users.id", ondelete="CASCADE")` in all three (matches the database; `alembic check` clean). No ORM `relationship` uses these tables (`user.py` has none), so ORM delete behaviour is unchanged. `warrior_audit_logs` FKs correctly have **no** cascade in both places (the test near `test_cyber_warriors_api.py:834` relies on that).
### 3.3 Index declarations that differ only by name or `DESC`

### 3.4 `elderly_configs.user_id` and `warrior_profiles.user_id`
- `elderly_configs`: database has `UNIQUE (user_id)` (constraint `elderly_configs_user_id_key`) **and** plain `ix_elderly_configs_user_id` (redundant: two btrees on one column). Proposed: keep both in the models so nothing changes: `user_id: ... unique=True` (no `index=True`) plus `__table_args__ = (Index("ix_elderly_configs_user_id", "user_id"),)`. Optional later (separate approval, not in this plan's migration): drop the redundant index and delete that `Index` line.
- `warrior_profiles`: database enforces uniqueness through constraint `warrior_profiles_user_id_key`; model has `unique=True, index=True` (a unique **index**). Proposed: drop `index=True`, keep `unique=True` (a unique constraint, equivalent and matching).
### 3.5 Database defaults on raw-SQL tables (58 columns)
`gen_random_uuid()`, `now()`, boolean/integer/JSONB literals and enum defaults exist in the database; the models supply the same values in Python (`default=...`). **Recommendation: do not declare them now.** Declaring them changes nothing at runtime (the Python default wins), `alembic check` does not compare defaults today (`env.py` leaves `compare_server_default` off), and a mismatched literal text would create permanent compare noise. Revisit only together with enabling `compare_type`/`compare_server_default`, generating the model text from the reflected database text. Note for future bypass inserts: `now()` is session-timezone time, the application writes UTC.
### 3.6 `otp_vault_entries` (protected)
Keep. `account_erasure.py:222` runs `DELETE FROM otp_vault_entries WHERE user_id = :u`; revision 1 creates it; its foreign key to `users` has no cascade, so the explicit delete is required before a user row can be removed. **Proposed guard (no model):** in `alembic/env.py` add an `include_object` hook that ignores exactly this table and its index when comparing, so `alembic check` and autogenerate can never propose dropping it:
```python
LEGACY_UNMODELLED_TABLES = {"otp_vault_entries"}  # still used by account erasure; created by revision 07cfca043074

def include_object(obj, name, type_, reflected, compare_to):
    if type_ == "table" and name in LEGACY_UNMODELLED_TABLES and reflected:
        return False
    if type_ == "index" and reflected and getattr(getattr(obj, "table", None), "name", None) in LEGACY_UNMODELLED_TABLES:
        return False
    return True
```
passed as `include_object=include_object` in `context.configure(...)` (offline and online). Alternative (not preferred): a minimal `OtpVaultEntry` model, which adds an unused ORM class.

## 6. The migration (needed: exactly one)
`alembic/versions/y0z1a2b3c4d5_sms_header_upper_index_and_audit_comment.py` (name proposed): `down_revision = "x9y0z1a2b3c4"`.
```python
def upgrade():
    op.create_index("ix_sms_sender_header_upper", "sms_sender_registry", [sa.text("upper(header)")])
    op.create_table_comment("warrior_audit_logs", "Append-only. Do not UPDATE or DELETE rows here.")

def downgrade():
    op.drop_table_comment("warrior_audit_logs", existing_comment="Append-only. Do not UPDATE or DELETE rows here.")
```

Properties: additive; no data read or written; no table rewrite; the downgrade removes only what the upgrade created. Name collision: `ix_sms_sender_header_upper` is not created by any earlier revision, so it is free in every database [V: searched all 26 revisions]. It does not touch the protected objects.
